# ADR 0001: Adopt-only migration — one non-destructive path into every vault

- Status: accepted
- Date: 2026-07-20
- Related: issue #4 (part of #1)

## Context

v3 needs to bring three very different starting points under management:

1. an empty directory (the `init` case),
2. an existing Obsidian vault full of user notes,
3. a legacy v2 vault, where v2 shipped skills, agents, examples, Dataview
   config, and generated files directly into the vault with **no manifest**
   and therefore no record of what it owns.

The v2 codebase answered this with several overlapping mechanisms: `init`
scaffolding, a `migrate` command, and an `update`/`workspace-sync` scan with
a hardcoded `DEPRECATED_FILES` list. Each had its own notion of what the CLI
owns, and none could prove it would not touch user content.

## Decision

There is exactly one way rubber-ducky enters or refreshes a directory: the
**adopt** engine (`src/lib/adopt.ts`). No separate migrate command, no
separate update scan, no separate init scaffold.

- **`init` is sugar for adopt.** `createWorkspace` delegates to
  `planAdopt` + `applyAdopt` on an empty directory; the only thing `init`
  adds is its empty-directory contract.
- **Dry-run is the default.** `rubber-ducky adopt` prints the full plan and
  writes nothing; only an explicit `--apply` executes it.
- **A managed-files manifest is the ownership boundary.** Adopt may only
  write files it records (content-hashed) in
  `.rubber-ducky/manifest.json`. Anything not in the plan is invisible to
  the engine — user notes are untouchable by construction, not by
  convention.
- **Managed vs seed roles.** Managed files (AGENTS.md, the two-line
  CLAUDE.md shim that imports it, `.claude/settings.json`, reference
  schemas, Bases `.base` views) are refreshed whenever the on-disk copy is
  provably ours: byte-equal to the current template, to the manifest's
  recorded hash, or to a known v2 fingerprint. Seed files (workspace.md,
  vault settings, .gitignore, context pages, .gitkeeps) are created once
  and never rewritten.
- **v2 vaults are recognized by content fingerprints.** Because v2 had no
  manifest, `src/lib/v2-fingerprints.ts` (generated by
  `scripts/generate-v2-fingerprints.ts` from the legacy repo — file assets
  hashed across its full git history, generated files from its HEAD
  generators) lets adopt *claim* byte-identical v2-shipped files:
  refreshing managed ones and removing vault-level skill/agent/example
  copies and the Dataview bootstrap. Skills are plugin-resident in v3; a
  stale vault copy would shadow them.
- **Modified means ask, never overwrite.** Any managed-role file that
  matches none of the known hashes is a conflict: interactively prompted in
  a TTY, reported with exit code 7 and requiring `--force` in
  non-interactive/JSON mode.
- **Bases replace Dataview.** The shipped views are `.base` files rendered
  by Obsidian's core Bases plugin, so the v2-era Dataview bootstrap is
  removed when byte-identical to what v2 shipped (and left alone when the
  user has customized it).

## Consequences

- Idempotency falls out of the design: a second `adopt --apply` is a
  byte-for-byte no-op (the manifest is only rewritten when something
  changed).
- Recognition of v2 generated files is HEAD-only: an intermediate v2
  release whose generated bytes differ will surface as a conflict instead
  of matching. That is the intended failure direction — an explicit
  question, never a silent overwrite — at the cost of an occasional prompt
  for genuinely unmodified files.
- The fingerprint module is a checked-in build artifact; regenerating it
  requires the legacy checkout, but CI and the compiled binary never do.
- Future template changes need no migration code: bump the template, and
  adopt refreshes unmodified copies everywhere while flagging edited ones.
